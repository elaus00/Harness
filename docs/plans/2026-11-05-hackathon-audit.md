# 시험용 Harness 기준 점검

후속 변경: 사용자가 clone 보관소와 응시 디렉터리를 분리하고 Docker 준비를 범위에서 제외했다. 현재 구현은 [파일 추출형 계획](2026-11-05-portable-exam.md)과 [START_HERE](../../START_HERE.md)를 따른다. 아래 판정은 보완 전 저장소를 대상으로 한 기록이다. 보관소에 README가 있는 것 자체는 현재 흐름의 결함이 아니며 추출본이 응시 원문을 보존하는지로 판단한다.

- 확인일: 2026-11-05 (Asia/Seoul)
- 범위: 사용자가 제공한 3층 구성 원칙과 현재 소스·문서·설치 도구의 대조.
- 판정: Docker 웹 앱의 기반은 있으나, 현재 저장소 전체를 그대로 시험용 하네스로 반입하기에는 미달한다.
- 이번 변경: Polars·humanizer-ko 동봉, 세 스킬 일괄 설치, 관련 AI 사용 규칙과 출처 기록. 앱 구조 전환은 수행하지 않았다.

## 우선 발견 사항

1. 저장소에는 루트·보일러플레이트·프론트엔드의 `README.md`가 있다. 따라서 “하네스에는 README를 두지 않는다” 기준에는 불일치한다. 하위 폴더에 clone하여 응시 루트 README를 보존하는 것과 하네스에 README가 없는 것은 다르다. 이번에는 기존 README를 수정·삭제하지 않았다.
2. 루트 `AGENTS.md`와 프로젝트 템플릿은 개인 개발 작업 규칙이다. 응시 README 수정 금지, 문서 우선순위, F·D·A 기록, 독립 검증기 규칙이 직접 적혀 있지 않다.
3. 기본 앱은 개인 업무 대시보드다. 통근버스 도메인이나 노선 가중치는 없지만, 프로젝트 분류·업무 상태·샘플 업무·전용 화면까지 정해져 있어 빈 시험용 기반으로는 과하다.
4. 설정·DB·헬스체크·인증은 제안된 운영 요건을 부분적으로만 만족한다. 데이터셋·생성·독립 검증·내보내기는 구현돼 있지 않다.
5. 이전 제안의 루트 `Decision.md` 대신 이번 기준인 `docs/DECISION.md`를 시험용 단일 기준으로 삼는 편이 적절하다. 현재는 둘 다 없고 `docs/decisions/`의 ADR만 있다.

## 2층: AI 작업 규칙

[현재 AGENTS](../../AGENTS.md)에는 문서 등록·검증·인계 원칙이 있고 이번에 두 스킬의 사용 조건도 추가했다. 시험용 규칙에는 다음을 보완해야 한다.

- 목적은 시험 전 비워 두고 현장 README를 읽은 뒤 한 문장으로 적는다.
- 응시 README 수정 금지, 비밀값 하드코딩 금지, validator의 engine 의존 금지를 본문에 직접 적는다.
- 응시 README, 확정 결정, 조사 자료의 우선순위를 명시한다. README와 충돌하는 결정은 README 수정의 근거가 될 수 없다.
- 사실 `F-001`, 결정 `D-001`, 가정 `A-001`을 구분하고 근거·상태·관련 ID를 기록한다. 미확인 가정을 확정 사실로 쓰지 않는다.
- 조사는 질문과 결정 ID에 연결하고 15분 상한을 둔다. 시간 경과를 가정 승인이나 사실 확인으로 간주하지 않는다.
- 실행·검사·Docker 명령과 완료 조건을 적는다. 검증기 미구현·미실행 상태를 “위반 0건”으로 보고하지 않는다.

시험용 흐름이 개인 컴퓨터의 전역 brainstorming·Impeccable이나 MCP에 의존해서는 안 된다. 전체 Superpowers 절차와 반복 승인도 짧은 시험의 상시 규칙으로 넣기에는 비용이 크다. 사용자 승인과 응시 규정이 요구하는 확인은 유지하면서 합의된 구현은 이어갈 수 있어야 한다.

## 3층: 반복 절차

| 절차 | 현재 상태 | 보완 방향 |
| --- | --- | --- |
| 요구사항 ID·수용 기준 | 전용 절차 없음 | 현장 README를 읽기 전에는 채우지 않는 체크리스트 절차 |
| 데이터 프로파일·교차 점검 | Polars 동봉 완료 | 별도로 행 의미·키·범위·담당자 질문·가정 후보를 산출하는 절차 필요 |
| 독립 검증기 작성 | 없음 | README·현장 Export 명세만 입력으로 제공. engine 코드·헬퍼·기대 출력에 의존하지 않는 검증 절차 |
| 정상 변경본·오류본 | 없음 | 원본 보존·출처 기록. 정상 변경, 규칙 위반, 계약 변경을 구분 |
| 중단 후 복귀 | 회고·status 기반 일부 있음 | INDEX·DECISION·진행 작업·마지막 검증을 읽는 절차. 종료 시 회고가 실행되지 않아도 복귀 가능해야 함 |
| 제출 문서 마무리 | 회고만 있음 | 확정 결정·실제 명령·검증·AI 사용을 공식 양식에 반영. AI_COLLABORATION 새 양식은 만들지 않음 |

Polars와 humanizer-ko는 이 절차를 돕는 도구 스킬이며 전체 절차를 대신하지 않는다. 메인·검증기·데이터의 최대 3세션 운영은 합리적인 시작안이다. 다만 매번 3개를 띄우기보다 해당 역할이 필요한 문제에서 분리하고 공통 계약은 README와 확정 결정으로 전달한다. 이번 점검에서는 별도 세션을 생성하지 않았다.

## 구조 판단과 권장안

세 층으로 나누는 방향은 적절하다. 다만 “문제와 무관한 것만”과 “데이터셋·생성기·두 역할을 전부 기본 구현”의 범위는 다르다. 역할 이름·권한, 데이터 행 의미·키·단위, 알고리즘·가중치, Export 컬럼은 문제를 보고 결정해야 한다.

공통 기반에는 Docker, 설정 처리, SQLite 저장·준비 확인, 오류 형식, 문서·스킬·복귀 절차를 둔다. 필수 환경변수는 실제 기능에 필요한 것만 지정한다. 인증은 선택 가능한 구현으로 준비하되 요구하지 않는 과제에서 로그인을 강제하지 않는다. 생성형 과제용 추가 구성으로 데이터셋의 원자적 교체·버전, 생성 잠금, 결과 버전 연결·재계산 표시, Export 전달 기능을 둔다. 실제 데이터·계획 스키마와 역할 정책은 현장에 남긴다.

시험 반입본의 목표 구조는 아래와 같다. 아직 생성하지 않은 제안이다.

```text
AGENTS.md
docs/
  INDEX.md
  DECISION.md
  PRD.md
  STATUS.md
  research/
.agents/skills/
app/
  backend/
  frontend/
engine/
validator/
datasets/
  original/
  valid/
  invalid/
tests/
output/
scripts/
compose.yaml
.env.example
HOW_TO_RUN.md
```

`README.md`와 `AI_COLLABORATION.md`는 반입본에 포함하지 않는다. 주최 측 파일은 응시 환경의 원래 경로에 그대로 둔다. INDEX는 문서 목록, DECISION은 근거·판단, STATUS는 진행 상황으로 구분한다. 빈 디렉터리는 Git이 보존하지 않으므로 필요한 자리에 `.gitkeep` 또는 실제 빈 인터페이스를 추적한다. research에는 사전 조사 문서를 넣지 않는다.

프론트엔드·백엔드가 나뉘면 Dockerfile도 각 빌드 컨텍스트에 둘 수 있다. 루트 Dockerfile 한 개라는 파일명 자체는 필수 원칙이 아니다. 평가가 루트 `docker build`를 요구할 때 그 진입점을 추가하고, 기본 실행은 루트 Compose 명령으로 명확하게 한다.

관리용 문서·기존 대시보드와 시험 반입본을 분리하는 전용 배포 브랜치 또는 배포 디렉터리를 권한다. 관리 저장소 전체를 응시 루트에 덮어쓰지 않는다. 반입 도구는 README·공식 양식을 제외하고 다른 기존 파일과 충돌하면 전체 적용 전에 중단하는 방식이 적절하다. 현재 `--skills-only`는 스킬 설치만 해결하며 앱·전체 뼈대 반입 도구는 아니다.

“시험에서는 엔진 두 개만 채운다”는 완료 보장은 할 수 없다. 현장 데이터 계약, 요구 화면, 권한, Export 명세와 수용 기준에 맞춘 작업도 남는다. 규칙·계약·공용 데이터 형식은 공유할 수 있지만 생성 알고리즘이나 생성기가 계산한 제약 판정값을 검증기가 재사용하면 독립 검증이 되지 않는다.

## 보완 순서

1. 사전 코드·스킬 반입과 clone 허용 여부 확인. 아직 허용됐다고 기록하지 않는다.
2. README·공식 양식을 제외한 시험 배포 범위와 짧은 AGENTS·INDEX·F/D/A·PRD·STATUS·실행 틀 정리.
3. 기존 대시보드를 기본 실행에서 분리하고 DB 준비 확인·웹 IDE 설정을 가진 최소 앱으로 검증.
4. 6개 반복 절차를 프로젝트 스킬·프롬프트로 준비하고 생성형 과제 추가 구성을 선택적으로 분리.
5. 깨끗한 clone의 Docker·DB 저장·재시작·README 보존 확인. 실제 웹 IDE에서도 접속·인증 검증.
6. 허용된 모의 문제·가짜 데이터로 3시간 리허설 후 시간 손실 반영. clone 실패 대비 핵심 지침·프롬프트의 붙여넣기용 사본 준비.

## 이번 변경의 검증

- `python3 -m unittest discover -s tests -v`: 9개 통과. 기존 6개 검사와 추가 3개 검사.
- 추가 검사: 스킬·참조 파일 해시 일치, 응시 README(BOM·CRLF 포함)·AI_COLLABORATION·AGENTS 바이트 보존, 미리보기 무변경·재설치 사용자 변경 보존, 스킬 심링크 충돌 시 다른 스킬도 생성하지 않음.
- 외부 스킬은 공식 원본 커밋에 고정했으며 기존 로컬 설치본과 본문이 같음을 확인했다. [동봉 기록](../../skills-bundle.lock.json)에 14개 파일의 해시를 기록했다.
- 앱 소스·Docker 구성은 변경하지 않았다. 앱 검사·Docker 재빌드·시험 웹 IDE 검증·AI 호스트의 실제 스킬 인식·3시간 리허설은 이번에 수행하지 않았다.
