# 작업 흐름

## 시작

프로젝트 지침 → 문서 색인 → 최신 상태 → 해당 작업의 결정·교훈 순으로 필요한 내용만 읽는다. 요청의 목표와 완료 기준을 확인한다. 기존 변경 사항과 실행 가능한 검증 명령을 먼저 확인한다.

## 설계와 실행

새 기능·큰 설계 변경에는 brainstorming을 사용한다. 이미 정해진 설계는 구현으로 이어가며 사소한 선택마다 재승인을 받지 않는다. 작은 작업은 대화의 짧은 계획으로, 긴 작업은 `docs/plans/`의 체크리스트로 관리한다. 계획에는 수정 대상, 검증 방법, 완료 조건을 함께 쓴다.

이 Harness는 Superpowers 전체 방법론을 설치하거나 강제하지 않는다. 현재 설치된 brainstorming의 설계 원칙과 writing-plans의 작업 분해 원칙을 참고하되, 문서 중심 작업에 테스트 우선 개발·worktree·추가 에이전트 사용을 일괄 요구하지 않는다. 구체적인 사용자 요청과 프로젝트 지침에 맞춰 절차를 조정한다.

## 검증

동작을 바꾼 부분을 중심으로 검증한다. 문서 변경은 링크·내용 일관성, 스킬 변경은 형식·실제 적용 조건, 적용 도구는 기존 파일 보존과 미리보기 무변경을 확인한다. 검증 실패를 숨기거나 실행하지 않은 검사를 통과했다고 보고하지 않는다.

## 회고와 인계

의미 있는 작업 완료 또는 종료 요청 시 clear-with-lessons를 사용한다. 재사용할 교훈은 원인·근거·해결·적용 범위로 기록한다. 현재 상태에는 다음 행동과 막힌 지점만 남기고, 사용자 조치는 `request.md`에서 관리한다. 교훈이 없으면 교훈 파일을 생성하지 않는다.

회고 지침은 작업 중 실행하는 절차다. 앱 강제 종료나 창 닫기를 감지하는 자동 훅은 포함하지 않는다. 회고가 끝나도 대화를 자동 초기화하거나 보관 처리하지 않는다.

## 개선 기준

3~5회 사용 후 반복 설명 횟수, 같은 실수의 재발, 불필요한 확인 요청, 세션 재개에 필요한 맥락을 점검한다. 반복 문제에 효과가 있는 규칙만 유지하고 사용하지 않는 지침은 줄인다.
